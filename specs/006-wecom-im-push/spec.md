# 006 — 企业微信群机器人推送

Triage: ready-for-agent
Date: 2026-08-25
Status: approved

## Problem Statement

日报目前只在本地 Web 端呈现:用户必须主动打开站点才能看到当期内容。作为自部署的单用户系统,用户每天真正常驻的地方是 IM(企业微信),日报"就绪了但用户不知道"。缺少一条把当期日报主动送达用户所在群的通道。

## Solution

日报生成流程末尾新增自动推送环节:每当一期日报状态变为 ready,即向用户配置的企业微信群机器人 webhook 发送一条 markdown 消息(标题 + Top N 条目摘要 + 完整日报链接),并在设置页提供 IM 推送配置(开关、多个 webhook、测试按钮)与日报页手动重推入口。第一期只接企业微信;通过轻量函数边界预留后续渠道扩展,不建注册表/插件机制。

## User Stories

1. 作为日报读者,我想在每天早上固定的企微群里收到当期日报的自动推送,这样不用主动打开站点也知道今天值得看什么。
2. 作为日报读者,我想在推送消息里看到 Top N 条目的标题和一句话摘要,这样在群里就能判断今天的内容是否值得深入。
3. 作为日报读者,我想点推送消息里的链接直接打开完整日报页,这样阅读体验不断裂。
4. 作为日报读者,我想让推送消息在超出企微 markdown 长度限制时自动截断条目并始终保留完整日报链接,这样消息永不因超长而发送失败。
5. 作为日报读者,当我没有配置可公网访问的日报地址时,我想收到不带链接的纯摘要推送,这样功能不因部署形态而报错。
6. 作为系统运营者(自部署用户),我想在设置页配置多个企微群 webhook,这样同一期日报能同时推送到不同的群。
7. 作为系统运营者,我想在设置页对每个 webhook 点"发送测试消息"立即验证配置,这样不用等第二天定时推送才发现 webhook 填错。
8. 作为系统运营者,我想在设置页看到脱敏显示的 webhook 地址,这样在共享屏幕演示时不会泄露凭据。
9. 作为系统运营者,我想让 webhook 地址明文留在提交框外(仅修改时提交完整地址),这样日常保存其他设置项时不会意外破坏已存的 webhook。
10. 作为系统运营者,我想在日报页看到当期推送状态(未推送/已推送/失败),这样能确认推送链路健康。
11. 作为系统运营者,我想在日报页点"重新推送"绕过防重直接再推一次,这样在群里误删消息或推送部分失败后能手动补救。
12. 作为系统运营者,我想让自动推送在同一期对同一 webhook 只成功推送一次,这样重复触发生成流程不会刷屏。
13. 作为系统运营者,我想让推送失败(网络抖动、企微限频)自动重试并指数退避,这样偶发故障不需要人工干预。
14. 作为系统运营者,我想让推送最终失败只记录状态和错误信息、绝不阻塞日报生成本身,这样推送故障不拖垮核心链路。
15. 作为系统运营者,我想让每个 webhook 的每次推送结果(成功/失败、错误摘要、时间)落库可查,这样排查问题有据可依。
16. 作为系统运营者,我想在日志里看到推送结果但永不看到 webhook 完整地址,这样日志可以安全地收集与分享。
17. 作为从未配置过 IM 推送的老用户,我想升级后一切照旧(默认关闭、存量设置兼容),这样不配置就不受影响。
18. 作为开源项目的贡献者,我想让推送逻辑收敛在一个干净的函数边界后面,这样增加第二个 IM 渠道是纯增量改动。

## Implementation Decisions

### 触发与编排
- 挂点在生成流程内部:日报状态迁移为 ready 的路径上调用推送(与生成入口无关——定时任务与手动重新生成都会触发),而非 scheduler 层包裹。
- 推送是生成主流程的"尽力而为"尾巴:任何推送异常被捕获、记录,不影响 issue 的 ready 状态与生成结果。
- 自动推送防重:同一 issueId + 同一 webhook 已有 success 记录则跳过;手动重推显式绕过防重。
- 手动重推与测试消息各一个端点,独立路由文件挂载,归入现有 /api/v1 前缀。

### 渠道与消息
- 第一期仅企业微信群机器人(custom webhook bot),消息类型 markdown,上限 4096 字节,超限按条目截断、链接兜底保留。
- Top N 条目取当期得分最高者,N 可配(默认 5,范围 3–10)。
- 消息结构:刊期标题 + 日期 → N 条(标题 + 一句话摘要)→ 完整日报链接。
- 日报链接由独立配置 link_base_url 与前端日报页路由拼接;link_base_url 留空则降级为无链接纯摘要(不报错)。不复用服务绑定 host(语义不同,改成公网域名会破坏启动)。

### 配置与安全
- settings 单例行新增 JSON 列 im_push:{ enabled, top_n, link_base_url, webhooks: [{name, url}] }。alembic 迁移加列,存量行为空对象。
- 默认 enabled=false,保证存量用户零感知。
- 严格校验(与现有 SettingsIn 风格一致):webhooks 最多 5 个;name 1–20 字符;url 必须匹配 qyapi.weixin.qq.com webhook 地址正则;top_n ∈ [3,10]。
- webhook URL 明文入库(自部署本地库);settings 读接口回显脱敏(尾 4 位可见);提交值等于脱敏占位符时视为"不修改原值";日志与错误信息永不包含完整 URL。
- 新增推送记录表:issue 标识 + webhook 标识 + 状态 + 错误摘要 + 时间;多 webhook 多行。

### HTTP 与重试
- 复用现有 async HTTP 客户端栈;重试用现有重试库(tenacity,已在依赖):3 次,2s/4s/8s 指数退避;对企微限频(频率限制)同样走退避。
- 渠道实现收敛为单个 notifier 模块,暴露 push(issue, webhooks) → 结果 的函数边界;不建 Notifier 协议、注册表或插件机制。

### 前端
- 设置页新增"IM 推送"配置区:总开关、top_n、link_base_url、webhook 列表增删改、逐 webhook 测试按钮。
- 日报页新增推送状态展示与"重新推送"按钮(按期操作)。

## Testing Decisions

- 好的测试只断言外部行为:API 响应、数据库落库状态、发出的 HTTP 请求内容;不断言内部调用序列或私有函数结构。
- **唯一新增测试接缝**:企微 webhook 的 HTTP 边界,用 respx mock qyapi.weixin.qq.com(dev 依赖已有,项目已配置覆盖率 80% 强制门槛)。
- 其余全部走现有接缝:
  - 触发/防重/重推/失败不阻塞:现有集成测试接缝(httpx 客户端打 app + 生成流程内测),先例为 settings 生效类集成测试。
  - markdown 渲染、超长截断、无链接降级、配置校验(正则/上限/占位符透传/脱敏回显):纯函数单测。
  - 重试行为:respx 模拟 5xx/限频序列,断言最终结果与落库状态。
- 不做真实企微 API 的端到端测试(webhook 是用户私有资源)。

## Out of Scope

- 企业微信以外的渠道(飞书/钉钉/Telegram/Slack/邮件)——留待第二期,设计上仅要求函数边界可增量扩展。
- IM 作为输入源(从群聊采集内容)与双向交互(群内对话查询/订阅)。
- 多租户/多订阅者模型;推送给"每个读者自己的 IM"。
- webhook URL 加密存储。
- 推送内容个性化(按群定制 Top N 之外的主题筛选);推送时间与日报生成时间解耦的独立调度。
