# Feature Specification: 日报个性化（评分体系 + 数量 + 风格）

**Feature Branch**: `002-daily-personalization`

**Created**: 2026-08-13

**Status**: Draft

**Input**: User description: "综合评分体系、`daily_count` 自定义、`style_mode` 三档"

## Clarifications

### Session 2026-08-13

- Q: 综合评分中的"来源权威性"维度应该用什么数据源来计算每个来源的权威分？ → A: 系统按信息源所属平台类型自动分配可信度等级与权重系数，等级排序为「官方博客 > 权威媒体 > 社区讨论」——由来源类型规则映射，不依赖 LLM 判断或外部指标。
- Q: 当同一事件被多源报道时，是否在 top-N 截取前做同质内容去重？ → A: 三层全局去重——单条内容全局唯一（URL 主键）、同一事件/主题跨平台仅保留传播热度最高的一条、观点高度同质化仅保留质量最优的一条。
- Q: 用户修改 `daily_count` 后希望何时生效？ → A: 仅下一期生效（每日 08:00 调度），不提供"立即重生成"按钮，与 001 系统「v1.x 无手动触发接口」契约一致；前端在保存后展示"下次生效时间"提示。
- Q: 切换 `style_mode` 时，是否也影响今日刊索引列表的展示密度，还是只影响右侧阅读器详情页？ → A: 三档同时影响索引列表和详情页；`concise` 档在列表中保留 标题+来源+评分，隐藏摘要/时间/阅读分钟数，在详情页只显示 标题+一句话总结+原文链接。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 看到综合评分并理解排序 (Priority: P1)

作为读者，我希望每篇文章都有一个 0–100 的综合评分（评分由多维信号合成，而非单一指标），并且能在条目列表与详情页看到分数与各维度提示，让我理解"为什么今天的头条是这篇"。

**Why this priority**: 综合评分是"摆脱算法投喂、让排序可解释"产品哲学的核心。没有评分，后续 `daily_count` 截取（P2）就失去依据——截取 top-N 必须基于可靠的排序信号；同时评分也是用户对内容质量判断的辅助锚点。它独立于风格切换，可单独交付。

**Independent Test**: 在今日刊页面，每条目都显示综合评分（如 87/100），点击详情后能看到各维度分数（如来源权威、内容深度、时效性、表达力）；同一来源不同文章评分不同，证明非简单来源加权。

**Acceptance Scenarios**:

1. **Given** 当日刊期已生成，**When** 用户打开今日刊，**Then** 每个条目在索引列表显示综合评分（整数 0–100），分数高的条目排在前面
2. **Given** 用户点击任意条目进入详情，**When** 详情页加载完成，**Then** 展示 3–5 个维度的子分数（如"来源权威 90 / 内容深度 85 / 时效 70 / 表达 80"），以及一句合成规则文字说明
3. **Given** 两篇评分相同（86 = 86），**When** 系统排序，**Then** 按次要键（如收录时间倒序）稳定排序，不出现随机跳动
4. **Given** 用户切换类型 chip 后筛选出子集，**When** 查看列表，**Then** 子集仍按综合评分降序
5. **Given** LLM 评分环节失败，**When** 单篇文章无法产出子分数，**Then** 系统回退到规则评分（来源权威 + 时效 + 长度启发式），综合分仍产出，不阻断刊期生成（与 FR-007a 容错策略一致）

---

### User Story 2 - 自定义每日条目数量 (Priority: P2)

作为读者，我希望在偏好设置里配置每天希望阅读的条目数量（如 10/20/30/40/50 五档可选，默认 30），系统按综合评分从高到低截取 top-N 进入当日刊，让我根据自己的阅读时长（15 分钟 / 30 分钟 / 60 分钟）调整信息密度。

**Why this priority**: 数量控制是"30 分钟深度阅读"承诺的关键调节阀。无数量控制则用户被迫浏览全部条目（信息过载）或被迫阅读少量条目（信息饥饿）。它依赖 P1 的综合评分作为排序依据，但截取逻辑可独立交付与验证。

**Independent Test**: 用户在偏好设置中将 `daily_count` 从 30 改为 10，保存后下一期刊（次日 08:00 生成）只包含综合评分 top-10 条目；用户重置设置为默认值后，下一期恢复 30 条。

**Acceptance Scenarios**:

1. **Given** 用户在偏好设置页，**When** 查看 `daily_count` 字段，**Then** 显示当前值（默认 30）并提供 10/20/30/40/50 五档单选
2. **Given** 用户将 `daily_count` 改为 10 并保存，**When** 保存成功提示出现，**Then** 提示文案明确写"已保存，下次 08:00 生效"，且当日已发行刊期不被重生成、UI 上不出现"立即重生成"按钮
2. **Given** 用户将 `daily_count` 改为 10 并保存，**When** 等待下一期刊生成（次日 08:00），**Then** 当日刊只包含综合评分 top-10 条目，索引列表数量徽标显示"共 10 条"
3. **Given** 当日候选文章池总数（如 80）小于配置的 `daily_count`（如 50），**When** 系统截取，**Then** 实际刊期只包含候选池全部条目（不补齐、不报错），数量徽标如实显示
4. **Given** 用户配置 `daily_count=10` 后切换类型筛选，**When** 查看筛选结果，**Then** 列表只显示当日已入选的 top-10 中匹配该类型的子集（不再重新截取，因为截取发生在生成期而非阅读期）
5. **Given** 用户重置设置为默认，**When** 重置完成，**Then** `daily_count` 回到 30，下一期生效

### User Story 3 - 三档风格切换阅读密度 (Priority: P3)

作为读者，我希望在偏好设置或阅读器顶部切换"简洁 / 标准 / 详细"三档阅读风格，影响文章详情的字段渲染白名单（简洁只显示标题+一句话总结+原文链接；标准显示默认字段；详细额外显示各维度子分数、引用块、全部正文段落），让我根据阅读情境快速调整信息密度。

**Why this priority**: 风格切换是"30 分钟承诺"的弹性调节——同一条目既可秒扫（简洁）也可深读（详细）。它独立于评分与数量，纯展示层可单独交付。

**Independent Test**: 用户在偏好设置选择"简洁"档并保存，刷新今日刊后点击任意条目，详情页只显示标题、一句话总结、原文链接；切换回"标准"档后刷新，详情恢复默认字段。

**Acceptance Scenarios**:

1. **Given** 用户在偏好设置页，**When** 查看 `style_mode` 字段，**Then** 显示当前档位（默认 `standard`）并提供 `concise / standard / detailed` 三选一
2. **Given** 用户选择 `concise` 并保存，**When** 刷新今日刊，**Then** 索引列表行只展示 标题、来源、综合评分（隐藏摘要、时间、阅读分钟数、类型），点击任意条目进入详情页只展示 标题、一句话总结、原文链接
3. **Given** 用户切换为 `detailed`，**When** 今日刊刷新，**Then** 索引列表行在 `standard` 基础上额外显示各维度子分数徽标，详情页额外展示子分数可视化与引用块
4. **Given** 用户在阅读器顶部临时切换档位，**When** 当前条目立即按新档位渲染，**Then** 不修改偏好设置（仅本会话生效），下次打开回退到设置中的默认档
5. **Given** 切换档位过程中断（如刷新页面），**When** 用户重新打开页面，**Then** 使用偏好设置中的默认档，不残留临时切换状态

---

### Edge Cases

- 当综合评分计算依赖的某个维度数据缺失（如新源无历史权威分、原文发布时间缺失）时如何回退？
- 当用户配置 `daily_count` 大于当日候选池总量时，是否在 UI 上提示"今日仅 N 条"？
- 当用户在生成期间（08:00 触发时刻）修改 `daily_count`，是影响本期还是下一期？
- 当 `style_mode` 切换的瞬时渲染失败（如某条目缺少详细档需要的字段）时如何降级？
- 当综合评分 top-N 中存在严重同质内容（同一事件多源报道）时，是否需要去重或散列？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每篇候选文章计算综合评分（0–100 整数），评分由至少 3 个维度的子分数合成
- **FR-002**: 综合评分 MUST 至少覆盖以下维度：来源权威性、时效性、内容深度、表达力（各维度 0–100 整数）
- **FR-002a**: 「来源权威性」维度 MUST 按「平台类型 → 可信度等级 → 权重」规则映射，由系统内置三档：
  - **官方博客**：产品/研究官方站点（如 OpenAI Blog、Anthropic News、Google AI、DeepMind、Hugging Face 等第一方发布渠道）
  - **权威媒体**：第三方独立报道/评论（如 MIT Tech Review、Simon Willison、Latent Space、Stratechery 等）
  - **社区讨论**：用户驱动型平台（X / Reddit / GitHub）
  - 等级排序固定为「官方博客 > 权威媒体 > 社区讨论」，每档对应固定的权威分基线（具体数值在 plan 阶段确定，例如 90/70/50）
  - 同一平台内不同账号/仓库不再细分（如 @karpathy 与普通账号同分；细分属于 v3）
- **FR-003**: 综合评分 MUST 在 summarizer 阶段产出，与 LLM 摘要一并持久化到文章记录
- **FR-004**: 当日刊期 MUST 按综合评分降序排列条目；同分时按收录时间倒序稳定排序
- **FR-005**: 系统 MUST 在偏好设置中暴露 `daily_count` 字段，取值限定为 `{10, 20, 30, 40, 50}`，默认 `30`
- **FR-006**: 当日刊期生成时 MUST 按综合评分从高到低截取前 `daily_count` 篇文章；候选池不足时全部入选
- **FR-007**: `daily_count` 配置变更 MUST 在下一期刊生效（不重生成当日已发行刊期）
- **FR-007a**: 系统 MUST 在 generator 阶段对候选文章池执行三层全局去重，去重后的池再按综合评分 top-N 截取：
  1. **URL 主键去重**：`sourceUrl` 完全相同的条目只保留综合评分最高的一条（沿用 001 系统 collector 层已做的 URL 去重的跨期扩展）
  2. **同事件/主题去重**：跨平台报道同一事件（如某 GitHub repo 同时被 OpenAI 博客引用、X KOL 转发、Reddit 讨论）时，仅保留**传播热度最高**的一条——热度 = 该事件跨源出现次数 × 最高综合分
  3. **观点同质化去重**：语义相似度极高的多篇内容（如多家媒体转载同一公告原文）仅保留**质量最优**的一条（按综合分判定）
  - 同事件/主题判定与观点同质化判定 MUST 在 summarizer 阶段由 LLM 输出 `topic_id` 与 `opinion_fingerprint` 两个字段（与摘要、评分同一次调用产出，避免额外 LLM 成本）
  - 三层去重 MUST 在 generator 截取 top-N 之前执行；去重被剔除的文章仍保留 raw_text 与评分（供未来检索/历史特性复用，本期不暴露）
- **FR-008**: 系统 MUST 在偏好设置中暴露 `style_mode` 字段，取值限定为 `{concise, standard, detailed}`，默认 `standard`
- **FR-009**: 今日刊 MUST 按当前 `style_mode` 同时控制索引列表与详情页的字段白名单：
  - `concise`:
    - 索引列表：仅 标题、来源、综合评分（隐藏摘要、收录时间、预计阅读分钟数、类型）
    - 详情页：仅 标题、一句话总结、原文链接
  - `standard`:
    - 索引列表：完整 7 字段（标题、摘要、类型、来源、收录时间、预计阅读分钟数，外加综合评分）
    - 详情页：标题、摘要、导语、正文、要点、原文链接、预计阅读分钟数
  - `detailed`:
    - 索引列表：在 `standard` 基础上额外显示各维度子分数徽标
    - 详情页：在 `standard` 基础上额外展示各维度子分数（带可视化）与引用块
- **FR-010**: 系统 MUST 支持在阅读器顶部临时切换 `style_mode`，仅本会话生效，不持久化
- **FR-011**: 当评分计算的 LLM 步骤失败，系统 MUST 回退到规则评分（来源权威 + 时效 + 长度启发式），并标记评分来源（`llm` 或 `rule_fallback`）以便调试
- **FR-012**: 详情页 MUST 展示一句简短的合成规则文字说明（如"综合分由来源权威 × 35% + 内容深度 × 25% + 时效 × 20% + 表达 × 20% 合成"），让用户理解排序依据

### Key Entities *(include if feature involves data)*

- **ArticleScore**: 文章评分快照。字段：综合分（0–100）、各维度子分数（dict，至少含 `authority` / `timeliness` / `depth` / `expression`）、来源权威等级（`official_blog` / `authoritative_media` / `community`）、评分来源（`llm` / `rule_fallback`）、计算时间戳。与 ArticleORM 1:1 关联。来源权威等级由「平台类型规则映射」决定（FR-002a），是 `authority` 子分的直接依据。
- **TopicCluster / OpinionFingerprint**: 由 summarizer LLM 在摘要阶段产出的两个字符串字段。`topic_id` 标识文章所述事件（同事件跨源相同）；`opinion_fingerprint` 标识观点特征（同质化转载高度相似）。两者用于 FR-007a 的二、三层去重，不进入阅读器 UI。
- **StyleProfile**: 风格档位定义。字段：档位名（`concise` / `standard` / `detailed`）、字段白名单（列表）、是否展示子分数、是否展示引用块。无持久化，作为系统内置枚举常量。
- **UserSettings（扩展）**: 在现有 `SettingsORM` 基础上新增 `daily_count: int`（默认 30，约束 10/20/30/40/50）与 `style_mode: str`（默认 `standard`，约束三档枚举）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从打开今日刊到识别今日头条评分理由，耗时不超过 5 秒（首屏可见分数 + 详情页一句话合成规则）
- **SC-002**: 用户修改 `daily_count` 后，从下一期刊生成到展示新数量，整体链路不超过 1 分钟（生成耗时不变，仅截取步骤额外消耗 < 1 秒）
- **SC-003**: 三档风格切换在阅读器中即时生效，从点击切换到详情完成重渲染不超过 500 毫秒（标准 p95）
- **SC-004**: 评分与去重信号（综合分、各维度子分、`topic_id`、`opinion_fingerprint`）MUST 与现有 summarizer 同一次 LLM 调用产出（追加 schema 字段），不显著增加调用次数；评分/去重相关字段引入的额外 token 成本不超过现有 summarizer 输入/输出 token 的 30%
- **SC-005**: 综合评分 top-10 文章对目标用户的"内容相关度"主观满意度 ≥ 80%（小范围用户调研，5 名以上用户各阅读 3 期）
- **SC-006**: 评分失败回退率 ≤ 5%（即 95% 文章成功产出 LLM 评分，仅 5% 走规则回退路径）

## Assumptions

- 现有 001-ai-daily-news 系统已稳定运行，4 信息源（X / GitHub / Reddit / Web）× 4 类型（Agent / Self-Improve / Open-Source / Tools）的契约不变；本特性在其基础上扩展 ArticleScore 字段、Settings 字段，不破坏 v1.x 接口
- 现有 summarizer 已调用 LLM 完成摘要；评分将作为同一次 LLM 调用的扩展输出（追加 schema 字段），不显著增加调用次数
- 综合评分的权重比例（如 35/25/20/20）由本特性首次确定，可在偏好或配置中暴露给资深用户调整属于 v3 范畴，本期固定
- 风格档位的字段白名单是产品决策（不是用户自定义），三档由系统内置；用户自定义字段白名单属于 v3 范畴
- 候选文章池在 summarizer 阶段全量产出评分，截取发生在 generator 末尾（top-N 持久化为当日 issue 的 articles 列表）；非选中文章保留 raw_text 与评分但不进入 issue 索引（供后续检索/历史特性复用，本期不实现检索）
- 用户偏好仍为单例 singleton（沿用 `SettingsORM.id=1`），本期不引入多用户/多 profile
