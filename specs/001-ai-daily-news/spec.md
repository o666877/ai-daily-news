# Feature Specification: AI 日报系统 (AI Daily News)

**Feature Branch**: `001-ai-daily-news`

**Created**: 2026-08-12

**Status**: Draft

**Input**: User description: "@PRD.md — 高度自定义的私人 AI 资讯聚合工具，每日固定时点生成『今日刊』，PC 本地网页端单页深度阅读（约 30 分钟），先个人本地部署使用，成熟后开源至 GitHub。本期 v1.x 严格对齐《后端集成接口文档 v1.0》的 9 个接口，固定 4 信息源 × 4 类型，开关式偏好下一期刊期生效；自定义信息源/标签/评分/检索/历史/已读等高级能力推迟到 v2。"

## Clarifications

### Session 2026-08-12

- Q: 没有可用的 X API token 时，本期应如何处理 X（Twitter）信息源？ → A: 采用 RSSHub 聚合方案（自部署 RSSHub 抓取 X 内容，作为 X 源的采集实现）；部署者未配置 RSSHub 时降级为静默跳过该源，不影响其他源采集，4 源契约与 `/meta` 元数据保持不变。
- Q: 当某个信息源采集失败时（如 RSSHub 宕机、Reddit 限流、GitHub API 500），刊期生成应如何处理？ → A: 部分失败容错——单源失败时跳过该源，剩余源正常采集并生成 `ready` 刊期；结构化日志记录失败源与失败原因；只有 LLM 摘要环节（重试 2 次仍失败）才会标记整期 `failed`。
- Q: 通过 RSSHub 采集 X 内容时，默认应跟踪哪些账号或列表？ → A: 内置默认账号清单（约 20-30 个 AI 领域 KOL，如 @karpathy / @simonw / @swyx 等），通过 RSSHub `/twitter/user/:id` 路由批量订阅；用户可经 `AIDAILY_X_ACCOUNTS` 环境变量覆盖默认清单。
- Q: 用户首次安装部署后、第一次到达推送时间（如 08:00）之前访问首页，应看到什么？ → A: 首次安装检测到无历史刊期时，后端自动后台触发一次初始生成（首次访问后约 5-10 分钟内可读首期）；该自动触发是内部行为不暴露为 API（与「v1.x 无手动触发接口」契约不冲突）；之后严格按调度在每日推送时间生成。
- Q: 本期 v1.x 应将哪个 LLM provider 作为默认推荐？ → A: 采用 Anthropic 兼容协议作为唯一集成层，支持自定义模型名（`AIDAILY_LLM_MODEL`）与自定义 base_url（`AIDAILY_LLM_BASE_URL`）；部署者可指向官方 Anthropic API、也可指向任何兼容 Anthropic 协议的服务（如 OneAPI 代理、DeepSeek、Moonshot 等转发层）。本期不实现 OpenAI / Gemini 适配器，简化为单一协议。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 阅读今日刊 (Priority: P1)

作为本地单用户，我每天固定时间（默认 08:00）打开 PC 本地网页端，希望在首屏一次性看到当天刊期的报头（日期、版次、状态）、按类型/来源分桶的数量徽标、以及当日所有条目的索引列表（标题、摘要、类型、来源、收录时间、预计阅读分钟数），点击任意条目即在右侧阅读器切换为详情视图，单次深度阅读约 30 分钟。

**Why this priority**: 这是产品的核心价值承载——『精简统一的每日信息入口』。没有今日刊浏览，整个产品失去存在意义。它覆盖了接口文档中 `GET /daily/today`、`GET /articles/{id}`、`GET /meta` 三个最核心读接口，也是 MVP 端到端链路（采集 → LLM 摘要 → 刊期 → 浏览）能否跑通的最小验证单元。

**Independent Test**: 启动本地服务后，用户访问首页，能看到当日刊期（或加载态/空态），点击任意条目能进入详情阅读，完成阅读后能通过「阅读原文」跳转到出处。整条链路独立可用，不依赖任何偏好设置或分享能力。

**Acceptance Scenarios**:

1. **Given** 当日刊期已生成且状态为 ready，**When** 用户打开首页，**Then** 首屏在 1.5 秒内可交互，报头展示日期/版次/状态徽标，索引列表展示全部条目的 7 字段（id、标题、摘要、类型、来源、收录时间、预计阅读分钟数），数量徽标按类型与来源分桶显示
2. **Given** 当日刊期正在生成中，**When** 用户打开首页，**Then** 页面展示骨架屏并自动轮询，刊期就绪后无刷新切换为正常态
3. **Given** 当前时间早于当日刊期生成时点（如 08:00 前访问），**When** 用户打开首页，**Then** 页面展示「正在翻今天的墙头」加载态而非错误
4. **Given** 当日刊期生成失败（LLM 摘要重试 2 次仍失败），**When** 用户打开首页，**Then** 页面行为与「未生成」一致，不展示原始错误堆栈
5. **Given** 用户在索引列表点击某条目，**When** 右侧阅读器切换为详情视图，**Then** 详情完整展示导语/一句话总结/正文段落/引用块（可选）/要点列表/原文链接/原文站点名/预计阅读分钟数/原文发布时间
6. **Given** 用户在详情视图点击「阅读原文」，**When** 浏览器新标签页打开，**Then** 直接跳转到该条目的原文链接，不经过中间页

### User Story 2 - 双维筛选今日刊 (Priority: P2)

作为读者，我希望通过类型 chips 和来源 chips 组合筛选当日刊期，例如『Reddit + Agent』，快速聚焦关心的细分内容，且筛选 chips 由后端元数据接口驱动、前端不硬编码。

**Why this priority**: 双维筛选是『摆脱算法投喂、用户主动控制阅读范围』产品哲学的关键交互。无筛选则用户被迫线性浏览全部条目，违背『精简』定位。本故事依赖 P1 的今日刊数据，但筛选逻辑可独立交付。

**Independent Test**: 在今日刊页面，用户依次点击任意类型 chip、任意来源 chip、以及两者组合，列表实时刷新并显示筛选结果或空态，后端响应回显当前筛选条件。

**Acceptance Scenarios**:

1. **Given** 用户在今日刊页，**When** 点击类型 chip（如『Agent』），**Then** 列表仅展示该类型条目，chip 高亮，响应中回显 `appliedFilters`
2. **Given** 用户已选类型 chip，**When** 再点击来源 chip（如『Reddit』），**Then** 列表展示同时满足类型与来源的组合筛选结果
3. **Given** 组合筛选无匹配条目，**When** 列表刷新，**Then** 展示「今天的货架是空的」空态
4. **Given** 后端将来新增信息源或类型，**When** 元数据接口返回新增项，**Then** 前端自动渲染新 chip，无需发版
5. **Given** 用户传入非法枚举值（如 `src=wechat`），**When** 接口返回业务码 1002，**Then** 筛选 chips 区域展示提示，不发起新请求

### User Story 3 - 配置我的偏好（下一期生效） (Priority: P3)

作为读者，我希望在设置面板控制 4 个信息源开关、4 个类型开关、每日推送开关及推送时间，保存后系统明确告知『下一期刊期生效』，且可一键恢复默认。

**Why this priority**: 偏好开关是本期 v1.x 唯一的用户可见『自定义』能力，对齐产品『高度自定义』定位的最小可落地形态。优先级低于 P1/P2 因为不配置任何偏好也能完整阅读。

**Independent Test**: 打开设置面板，回填当前偏好，修改若干开关与推送时间，点击保存，看到生效刊期提示；再次打开面板验证修改已持久化；点击恢复默认验证回到全开 + 08:00。

**Acceptance Scenarios**:

1. **Given** 用户首次打开设置面板，**When** 面板加载，**Then** 调用读接口回填当前偏好（信息源 4 开关、类型 4 开关、推送开关、推送时间），调用元数据接口渲染开关列表（不硬编码）
2. **Given** 用户修改若干开关与推送时间，**When** 点击保存偏好，**Then** 全量提交当前开关状态，响应头 `X-Effective-At` 告知下一期生效刊期（如 `20260813`），UI 提示『明天的日报将按新口味调配』
3. **Given** 偏好已保存，**When** 用户刷新页面或重新打开面板，**Then** 上次保存的状态被正确回填
4. **Given** 用户在面板点击恢复默认，**When** 系统执行重置，**Then** 所有信息源与类型开关回到『开启』、推送时间回到 08:00、推送开关回到开启，面板展示返回的默认值
5. **Given** 用户填写了非法推送时间（如 `25:00`），**When** 提交保存，**Then** 接口返回业务码 1005，表单级提示注明字段
6. **Given** 当前刊期已生成，**When** 用户保存新偏好，**Then** 当期不回溯重算，下一期刊期生成立即按新偏好采集

### User Story 4 - 分享一条资讯 (Priority: P4)

作为读者，我希望在详情视图对任意条目生成一张分享卡片，得到可复制/可打开的卡片链接，便于把当日读到的优质内容分享给同行。

**Why this priority**: 分享是『精简入口』之外的次要扩散价值，并支撑后续开源社区传播。不分享不影响核心阅读体验，因此 P4。

**Independent Test**: 在任意详情视图点击「分享这条」，得到卡片 URL 与标题预览，复制后可在浏览器打开预览。

**Acceptance Scenarios**:

1. **Given** 用户在详情视图，**When** 点击「分享这条」，**Then** 系统为该条目生成分享卡片，返回卡片 ID 与卡片 URL，UI 展示卡片标题便于分享前预览
2. **Given** 用户尝试对不存在的文章发起分享，**When** 系统返回业务码 2001，**Then** UI 提示『文章不存在』
3. **Given** 用户未登录或无写权限 token，**When** 发起分享，**Then** 系统返回业务码 1003，UI 跳转登录

---

### User Story 5 - 异常态优雅呈现 (Priority: P5)

作为读者，我希望在网络异常、限流、服务内部错误、采集管线繁忙等情况下，看到稳定的错误提示而非崩溃页面，并能重试或继续浏览。

**Why this priority**: 错误态是用户对产品质量的体感底线。本期 v1.x 接口文档定义了 7 类业务错误码，全部需要前端落到稳定 UI 表现。优先级靠后因为属于体验完整性而非 MVP 必备。

**Independent Test**: 模拟各类错误响应（缺少必填参数、非法枚举、校验失败、限流、500、503），观察 UI 是否按错误码表稳定呈现。

**Acceptance Scenarios**:

1. **Given** 接口返回业务码 1001（缺少必填参数），**When** 前端展示，**Then** 表单级提示明确字段
2. **Given** 接口返回业务码 1006（触发限流），**When** 前端展示，**Then** Toast 提示『操作太频繁，稍后再试』
3. **Given** 接口返回业务码 9001（服务内部错误），**When** 前端展示，**Then** 全局错误态 + 重试按钮，不展示原始错误堆栈或敏感字段
4. **Given** 接口返回业务码 9002（采集/摘要管线繁忙），**When** 前端展示，**Then** 全局错误态 + 重试按钮
5. **Given** 任意错误响应体，**When** 前端解析，**Then** 仅含 code/message/requestId 三个字段，绝不包含内部栈、SQL、密钥
6. **Given** 用户在任意步骤遇到错误，**When** 点击重试，**Then** 系统重新发起上次请求，不丢失当前筛选与偏好上下文

### Edge Cases

- 当前时间刚好等于刊期生成时点（如 08:00:00），刊期可能正处于 `generating → ready` 转换瞬间：前端应保留骨架屏 + 轮询，不报错
- 用户在保存偏好后立即关闭浏览器、下一期生成时未在线：偏好仍应在下一期刊期生效（异步生效语义）
- 用户连续多次点击保存偏好：依赖全量覆盖幂等性，重复提交不应导致状态损坏
- 用户尝试通过浏览器历史回退到已删除/不存在的文章详情：应展示『内容不存在』而非崩溃
- 用户在未认证状态下访问首页读接口：读接口匿名可用，应正常展示；尝试访问写接口（保存偏好、分享）时才提示登录
- 元数据接口返回的开关列表为空（极端情况）：前端应展示空态而非崩溃，且不硬编码兜底列表
- 用户在筛选 chip 上多次快速切换：应做防抖处理，避免并发请求竞态
- 首次安装部署后用户立即访问首页：后端已在后台触发初始生成（FR-001b），前端首屏看到「正在翻今天的墙头」加载态（业务码 2002），5-10 分钟内自动轮询切换为 `ready` 刊期；用户无需等到次日 08:00
- 刊期生成失败标记为 `failed` 时与"未生成"行为一致（业务码 2002）：前端不应区分两种内部状态
- 单源采集失败（如 RSSHub 宕机）：跳过该源，其余源正常采集，刊期状态由 LLM 摘要环节决定（前端无感知，仅后端日志可见）

## Requirements *(mandatory)*

### Functional Requirements

#### 信息源与类型体系（本期固定）

- **FR-001**: 系统 MUST 支持固定 4 个信息源——`x`（X/Twitter）、`github`（GitHub）、`reddit`（Reddit）、`web`（全网聚合），本期不支持用户新增或删除信息源。其中 `x` 源默认通过自部署 RSSHub 抓取（部署者未配置 RSSHub 时该源静默跳过，`/meta` 与 Settings 仍保留 `x` 枚举不变）
- **FR-001a**: 系统 MUST 为 `x` 源维护一份默认账号清单（约 20-30 个 AI 领域 KOL），通过 RSSHub `/twitter/user/:id` 路由批量订阅；用户可通过 `AIDAILY_X_ACCOUNTS` 环境变量（逗号分隔的 X 用户名清单）覆盖默认清单；清单为空时 `x` 源静默跳过
- **FR-001b**: 系统 MUST 在后端启动时检测数据库中是否存在任何历史刊期；不存在则立即在后台触发一次初始刊期生成（不等推送时间），首次访问用户在 5-10 分钟内即可读到首期内容；该触发是内部行为，不暴露为 API，与「v1.x 无手动生成接口」契约不冲突
- **FR-002**: 系统 MUST 支持固定 4 个内容类型——`agent`（智能体）、`self_improve`（持续学习）、`open_source`（开源）、`tools`（工具效率），本期不支持用户新增或删除类型
- **FR-003**: 系统 MUST 通过元数据接口向所有筛选 chips、设置面板开关列表提供 4 源 + 4 类型的权威元数据，前端 MUST NOT 硬编码这些列表
- **FR-004**: 系统 MUST 视 `blogs` 枚举为 `reddit` 的历史别名（2026-08-12 起更名），历史数据按映射规则处理

#### 今日刊与详情

- **FR-005**: 系统 MUST 每日在用户配置的推送时点（默认 08:00，时区 Asia/Shanghai）自动生成当日刊期，刊期状态机为 `generating → ready / failed`
- **FR-006**: 系统 MUST 在刊期生成中对每条采集内容生成 5 类 LLM 加工文本：导语、一句话总结、正文段落（多条）、引用块（可为空）、要点列表
- **FR-006a**: 系统 MUST 通过 Anthropic 兼容协议与 LLM 服务通信；模型名（`AIDAILY_LLM_MODEL`）与 base_url（`AIDAILY_LLM_BASE_URL`）必须可经环境变量配置；本期不实现 OpenAI / Gemini 协议适配器
- **FR-007**: 系统 MUST 在 LLM 摘要失败时自动重试最多 2 次，仍失败则将当期刊期标记为 `failed`
- **FR-007a**: 系统 MUST 在单源采集失败时（HTTP 超时/限流/解析错误）跳过该源继续采集其他启用的源，刊期状态仍按 LLM 摘要结果决定（`ready` 或 `failed`），失败源与失败原因写入结构化日志便于排障
- **FR-008**: 系统 MUST 通过今日刊接口返回刊期 ID、日期、版次、状态、生成完成时间、条目总数、本期实际采集范围（`filtersApplied`）以及条目索引列表
- **FR-009**: 条目索引列表 MUST 仅含 7 字段（id、标题、摘要、类型、来源、收录时间、预计阅读分钟数）；长文字段（导语/正文/引用/要点/原文链接/原文站点名/原文发布时间）仅在详情接口返回
- **FR-010**: 系统 MUST 通过数量徽标字段（按类型分桶 + 按来源分桶）支持前端渲染数量标识
- **FR-011**: 系统 MUST 通过详情接口返回完整条目字段（含正文段落、要点、引用块、原文链接、原文站点名、预计阅读分钟数、原文发布时间）
- **FR-012**: 「阅读原文」操作 MUST 直接使用条目的原文链接在新浏览器标签页打开，系统 MUST NOT 单独提供跳转接口或缓存原文全文

#### 双维筛选

- **FR-013**: 系统 MUST 支持按类型与来源的组合筛选，参数同时传入时为 AND 关系
- **FR-014**: 系统 MUST 在筛选响应中回显当前应用的筛选条件（`appliedFilters`）
- **FR-015**: 系统 MUST 支持分页参数（页码从 1 起，每页大小默认 20、最大 50）
- **FR-016**: 系统 MUST 对非法枚举值（不在 4 源/4 类型之内）返回业务码 1002

#### 用户偏好

- **FR-017**: 系统 MUST 持久化三类用户偏好：4 个信息源开关、4 个类型开关、每日推送开关 + 推送时间（HH:mm 24 小时制）
- **FR-018**: 系统 MUST 在偏好保存后通过响应头 `X-Effective-At`（格式 YYYYMMDD）告知前端下一期生效刊期
- **FR-019**: 系统 MUST 保证偏好保存后**下一期刊期生成立即生效**，当期不回溯重算
- **FR-020**: 系统 MUST 支持一键恢复默认——所有信息源与类型开关回到开启、推送开关开启、推送时间 08:00
- **FR-021**: 系统 MUST 对推送时间格式校验失败（如 `25:00`）返回业务码 1005
- **FR-022**: 系统 MUST 保证偏好保存接口的全量覆盖幂等性，重复提交不产生副作用

#### 分享

- **FR-023**: 系统 MUST 支持对指定条目生成分享卡片，返回卡片 ID、卡片 URL、卡片标题（用于分享前预览）
- **FR-024**: 系统 MUST 对分享不存在的文章返回业务码 2001

#### 元数据与健康检查

- **FR-025**: 系统 MUST 提供健康检查接口，返回整体状态、版本号、采集与摘要子系统的健康状态——用于联调与监控，不展示给终端用户

#### 通用约束

- **FR-026**: 系统 MUST 对读接口允许匿名访问；对写接口（保存偏好、恢复默认、生成分享）要求身份凭证
- **FR-027**: 系统 MUST 对读接口限流 120 次/分钟/IP，对写接口限流 30 次/分钟/用户，超限返回业务码 1006
- **FR-028**: 系统 MUST 对所有错误响应返回统一结构（业务码、人类可读消息、请求 ID），绝不返回内部栈/SQL/密钥
- **FR-029**: 系统 MUST 支持客户端透传请求 ID 头，响应同值返回，便于跨请求排障
- **FR-030**: 系统 MUST 仅支持简体中文界面，时间格式遵循 ISO 8601 + Asia/Shanghai 时区，列表收录时间用 `HH:mm`、刊期日期用 `YYYY-MM-DD`

### Key Entities *(include if feature involves data)*

- **DailyIssue（刊期）**：每日一期的容器。关键属性：刊期 ID（YYYYMMDD）、日期、版次（第 N 版）、状态（生成中/就绪/失败）、生成完成时间、条目总数、本期实际采集范围（来源自用户偏好）。一条 Article 必属于一个 DailyIssue。
- **Article（资讯条目）**：每日刊期中的一条内容。关键属性：条目 ID、所属刊期 ID、类型、来源、标题、列表摘要、导语、一句话总结、正文段落（多条）、引用块（可空）、要点列表、收录时间、原文链接、原文站点名、预计阅读分钟数、原文发布时间。Article 在列表与详情两种视图中暴露不同字段子集。
- **Source（信息源）**：固定的 4 个采集渠道元数据。关键属性：key（x/github/reddit/web）、展示名、短名、图标 key、一句话描述。
- **Type（内容类型）**：固定的 4 个内容分类元数据。关键属性：key（agent/self_improve/open_source/tools）、展示名、短名。
- **Settings（用户偏好）**：单用户的偏好集合。关键属性：4 源开关 map、4 类型开关 map、每日推送开关、推送时间、最后修改时间。本期不含每日条数、风格档位、生成时点、永久筛选状态、已读列表等扩展字段。
- **ShareCard（分享卡片）**：针对一条 Article 生成的可分享卡片。关键属性：分享 ID、卡片 URL、对应文章标题。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从打开首页到首屏可交互并开始浏览当日刊期的总耗时 ≤ 1.5 秒（本地部署场景）
- **SC-002**: 用户在今日刊页面点击任意条目到详情视图内容呈现完成的等待时间感知为『即时』（人眼可察觉卡顿阈值以内）
- **SC-003**: 用户每日单次深度阅读时长稳定在约 30 分钟区间内，刊期内容规模与质量支持该阅读模式
- **SC-004**: 100% 的用户偏好修改在下一期刊期生效，不出现『当期回溯』或『偏好丢失』情况
- **SC-005**: 100% 的错误响应绝不向用户展示内部栈、SQL、密钥等敏感信息（仅业务码 + 消息 + 请求 ID）
- **SC-006**: 任意一期的刊期生成失败率（LLM 摘要重试 2 次仍失败） ≤ 5%，且失败时前端表现稳定可重试
- **SC-007**: 90% 的用户在首次使用产品时无需文档即可完成『浏览今日刊 → 筛选 → 详情 → 阅读原文 → 设置偏好』主路径
- **SC-008**: 100% 的筛选 chips 与设置面板开关由元数据接口驱动，前端代码中无任何信息源/类型的硬编码字面量
- **SC-009**: 用户在 7 类业务错误码（1001/1002/1003/1005/1006/9001/9002）任一场景下都能看到稳定、可理解的 UI 反馈与重试入口
- **SC-010**: 系统 P95 单条详情读取耗时 ≤ 200 毫秒，列表 + 筛选 + 分页 P95 ≤ 300 毫秒，今日刊首屏 P95 ≤ 500 毫秒（本地部署）
- **SC-011**: 后端新增信息源或类型时，前端在不动代码、不发版的情况下即可在 chips 与设置面板自动展示新增项

## Assumptions

- **部署形态**：v1.x 为本地单用户 PC 网页端部署，单机可用性即可，不要求 7×24 在线；进程重启后能恢复到上次状态
- **X 源采集**：部署者无 X API token（默认情况）；X 源通过自部署 RSSHub（开源 RSS 包装器）抓取，RSSHub 端点通过 `AIDAILY_X_RSSHUB_BASE_URL` 环境变量配置。未配置时 X 源静默跳过，其他 3 源正常采集，`/meta` 与 Settings 中的 `x` 枚举保持不变（4 源契约不破）。默认订阅 20-30 个 AI 领域 KOL 账号清单（如 @karpathy / @simonw / @swyx 等），用户可通过 `AIDAILY_X_ACCOUNTS` 环境变量覆盖
- **接口契约权威性**：本期 v1.x 严格对齐《后端集成接口文档 v1.0》，接口文档为本期范围的权威契约；若 PRD 与接口文档冲突，以接口文档为准
- **时区与语言**：本期仅支持简体中文界面、Asia/Shanghai（UTC+8）时区、ISO 8601 时间格式
- **认证模型**：读接口匿名可用，写接口（保存偏好、恢复默认、生成分享）需要身份凭证；具体认证机制由后端决定
- **LLM 集成**：本期仅支持 Anthropic 兼容协议；部署者通过 `AIDAILY_LLM_BASE_URL` 指定服务端点（默认 `https://api.anthropic.com`）、通过 `AIDAILY_LLM_MODEL` 指定模型名、通过 `AIDAILY_LLM_API_KEY` 提供密钥；可指向官方 Anthropic API 或任何兼容转发服务（OneAPI / DeepSeek / Moonshot 等）。本期不实现 OpenAI / Gemini 适配器
- **本期范围外（推迟到 v2）**：自定义信息源 CRUD、自定义标签 CRUD、每日条数（daily_count）配置、风格档位（style_mode）、当日核心结论（conclusions）、按领域分组快照（sections）、综合评分体系（score）、永久筛选状态（src_filter）、手动立即生成、当日日报重算、历史日历、历史日报访问、关键词检索、已读跟踪——上述能力本期 v1.x 一律不实现
- **本期永不实现（与产品哲学冲突）**：多用户/账号体系、移动端/原生 App、推送通知（邮件/IM）、收藏/标注/笔记、算法个性化推荐、RSS/Atom 输出、原文全文缓存与搜索、热度图/阅读统计仪表盘
- **数据合规**：信息源抓取需遵守目标平台 robots/ToS；原文链接仅做跳转不缓存全文；用户偏好属于私人数据不可外发，开源版需明确告知部署者数据归属
- **默认值基线**：4 源全开、4 类型全开、每日推送开关开启、推送时间 08:00、分页 page=1、pageSize=20（最大 50）、读限流 120/min/IP、写限流 30/min/用户
- **生成时点**：刊期默认在用户推送时间（默认 08:00）按当前生效偏好生成；本期不提供手动触发接口（推迟到 v2）
